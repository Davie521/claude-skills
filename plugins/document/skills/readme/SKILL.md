# readme

README 是读者对一个仓库的第一眼，很多人也只看这一眼。它要做的不是推销，而是让每个读者**尽快判断这东西适不适合自己**，包括尽快发现不适合、然后离开。所以 README 要写成一个漏斗：最影响去留的事实放最上面，越往下越细，细到只有决定留下的人才需要的程度，就该离开 README、进 `docs/` 了。

README 同时是一份契约：它说这个项目做什么、怎么用，读者照着做就该得到那个结果。所以 README 里的每条命令、每个数字都必须是真的。一句编出来的参数比少写一句更伤人，因为读者会照做，然后失败。

这两条是下面所有规则的来源。碰到规则没覆盖的情况，回到这两条去判断。

## 默认立场

- 作者写的 README 往往是在推销，不是在帮读者做判断。审的时候先问：读者读完第一屏，能不能决定「要 / 不要」？
- README 里的说法默认不可信，直到在代码、日志、CI 里找到出处为止。旧 README 也一样：作者写的时候是对的，现在不一定还对。
- 功能列表是作者想让你看的，用法和限制才是读者要的。
- 写得像 AI 不是因为用了某种格式，而是因为说了核对不了的话。改 AI 腔先删空话，不是先改格式。

## 硬性边界

**信息守恒。** README 里每一条事实（命令、路径、数字、默认值、版本、功能、限制）都要能指出出处：`文件:行`、日志、CI 记录、实测输出。指不出来就不写。改写已有 README 时：

- 不许新增原来没有、代码里也找不到的功能、数字、用户评价、效果宣称。
- 不许删掉限制和限定说法（「仅 macOS」「实验性」「免费版没有」），也不许把「可能」改成「会」。
- 作者写的内容是「搬走」不是「删掉」：搬去 `docs/` 并留链接。过时、错误的可以删，但要在汇报里写明删了什么、为什么删。

**不碰的东西。** 协议文本、作者署名、致谢、作者喜欢的装饰（徽章、logo、star 曲线），没有用户同意不改不删。

## 必须停下来问用户的地方

下面这几处必须停下来，等用户回复再继续，不要默认往下做：

1. **读者是谁拿不准时**：比如仓库既像公开工具又像私人脚本。
2. **要删作者写的整节内容或装饰时**：先列出来要删什么、为什么删。
3. **缺真实截图或产物样例时**：请用户提供，不要拿旧图凑，也不要自己造。
4. **发现协议和宣传的用法互相矛盾、仓库里有私人信息、Demo 挂了时**：告诉用户，不替他改协议、删文件、改部署。审查模式下不用中断，写进报告就行。
5. **改 GitHub 上的东西之前**：改 About 描述、推送、开 PR，都要先问。

## 哪些不归这个 skill

- 写完整的文档站、教程、API 参考：那是 `docs/` 的活，README 只给它们指路。
- 逐句清理中文 AI 腔：交给 `lieflat-less-ai-tone`。本 skill 只处理 README 特有的写法（见 [references/ai-tone.md](references/ai-tone.md)）。
- 检查 Markdown 锚点渲染、gh 的怪问题：见 `gh-pr-traps`。
- README 已经好用，用户只是想换个风格：没有读者受益的改动不做。
- 只想改一个错字、补一行：直接改，不用走下面的流程。

## 流程

### 1. 先弄清是谁在读

不同读者要的东西完全不同，弄错读者，后面每一步都会偏。

| 仓库类型 | 读者，以及他们最想知道什么 | 漏斗顺序 |
|---|---|---|
| 工具 / App / CLI | 路过的陌生人：这是什么、长什么样、装得上吗 | 一句话 → 真实画面 → 「为什么」 → 最小可运行例子 → 怎么装 → 限制 → 细节链接 |
| Agent skill / 模板 / MCP / AI 工具 | 想让 agent 替自己干活的人：说一句什么话，会得到什么，靠不靠谱 | 一句话承诺 → 第一句要打的话和接下来会发生什么 → 痛点和思路 → 真实产物 → 为什么有效、证明过什么 → 安装（装哪个目录、怎么确认）→ 边界 |
| 库 / SDK | 要调用它的开发者：接口顺不顺手 | 一句话 → 最小可运行示例及其输出 → API 概览或链接 → 安装 → 限制 |
| 有在线 Demo 的 Web App | 想先试的人；只有少数人会自己部署 | 一句话 → 截图和 Demo 链接 → 自托管（必填配置、外部服务、部署限制） |
| 私人工具 / 运维仓库 | 将来的自己、接手的 agent：要做 X 该读哪份、碰哪里会坏 | 一句话（是什么、跑在哪）→ 按任务指路 → 目录 → 不显然的决定 → 怎么装 → 出问题怎么办 |
| 课程作业 / 研究 | 老师、面试官：做了什么、结果如何 | 一句话 → 结果（数字或图）→ 怎么复现 |

库把安装放在 API 后面，是因为读者要先看接口合不合用，才愿意去装。App 没有接口给人看，所以装法紧跟在画面后面。

看不出读者是谁就问用户一句。别按开源项目的默认模板去写一个配置文件夹。

### 2. 收事实

动笔前先读代码，把 README 要写的事实逐条列出来，每条都带上出处（`文件:行`）：

- 安装脚本**实际**做了什么：装到哪、改了用户的哪些设置、不碰什么
- 配置项：变量名、默认值，哪些是必填。代码、`.env.example`、compose 文件三处要对上
- 行为里的具体数字：阈值、间隔、上限
- 依赖和最低版本：以 CI 真跑过的版本为准
- 外部服务：OAuth、第三方 API、构建时要联网抓的东西，以及它们挂掉时项目会怎样
- 限制：免费版缺什么、哪些平台不支持
- 卸载：安装时改过的每一处，都要有对应的撤销步骤

核实不了的说法不写进 README，交付时单独告诉用户。

### 3. 先审，再改

已有 README 的话，先从头读一遍，对照漏斗找下面这些毛病。它们是真实审查里最常见的：

- **读者混在一起。** 发版流程、CI 密钥表、目录树、调试指南，和给用户看的内容搅在一起。这是最常见、伤害最大的一种。`CLAUDE.md`、`AGENTS.md` 也算这一类：它们是写给 agent 的指令，不能当成「架构文档」从 README 推荐给读者。例外是专门写给 agent 照着做的文档，比如 `docs/agent-install.md`，可以从安装一节链过去。
- **漏斗塌了。** 前 50 行就在讲内部实现，读者还不知道这东西是不是给自己的。
- **同一件事说了几遍。** 版本号、阈值在三个地方各说一次，迟早有一处会过时。
- **过时。** 链接失效、提到已删除的文件，命令早就改了。
- **说法比代码大。** 写着有的功能其实没有，写着「可选」的其实是必填，没实现的写成已有。
- **读起来像生成的。** 按 [references/ai-tone.md](references/ai-tone.md) 的白名单逐条找：空形容词、emoji 小标题、功能名代替功能、推销式开头、编造的数字、空占位小节……每条都有触发标记。那份文件里还有一张「不作为修改理由」表：问题小标题、README 很长、粗体开头的功能列表，这些高星仓库里人写的也常见，不能当毛病。

动手前还有三件事：
1. 跑 `git status`。工作区不干净就别直接改，README 可能带着作者还没提交的东西。
2. grep 一下测试和 CI 里有没有钉死 README 文字的断言（标题、文件列表），否则改完 CI 会红。
3. 看看有没有派生副本（`README.zh-CN.md`、官网文案、包管理器上的描述），它们要一起改，或者明确说这次不改。

用户只要审查的话：不动任何文件，跳过第 4 步，但第 5 步的核验照做（能安全跑的命令就跑，跑不了的从代码推断），然后按「汇报」一节的格式出报告。

### 4. 写

按第 1 步的漏斗顺序写。下面每一条都能在用户 star 过的高星仓库里找到真实写法，原文摘录见 [references/examples.md](references/examples.md)。

- **一句话说效果，不说技术。** 读者要知道的是「它替我做了什么」，不是「它用什么写的」。比如「Describe a game. Claude Code asks a few questions, writes a one-page brief, and builds a playable browser game from it.」GitHub 仓库的 About 描述要和这句说的是同一件事。
- **紧接着说为什么需要它，站在读者的处境说。** 比如 process-compose 的「**Why?** Because sometimes you just don't want to deal with docker files…」。也可以先说出读者现在用的那个不好用的办法，再说这个项目换了什么思路（「不要让 agent 直接模仿，而是先……」）。
- **先给用法，再给功能。** 第一节放读者要打的第一条命令、第一句话，或者最小可运行的配置，再用几步写清楚之后会发生什么。读者看完就知道这东西怎么用、会产出什么。功能列表放在后面。
- **紧接着放真实的东西。** 实机截图、真实输出、录屏都行。读者信眼睛不信形容词，mockup 和 AI 生成的图会让人起疑。先去仓库里找（`docs/`、`screenshots/`、release 附件），常常已经截好了只是没用上；截图必须和现在的界面一致，导航、文案已经改过的旧截图会让读者以为东西没维护。真没有合适的就留空，请用户截，不要自己造。
- **功能写得具体。** 每条是粗体短句加具体做法，带上读者能核对的数字或文件名（「不足 60 页时按规则生成全部代码材料」）。能力本身就具体时，一行短语也够了（`Health checks (liveness and readiness)`）。「智能」「无缝」这类词读者核对不了。
- **给出真实产物。** 产出是文件的（文档、配置、报告），把一份样例提交进仓库并链过去；产出是界面的，就放截图或录屏。
- **证明过什么就写什么，样本小就说样本小。** 有对比测试就写测试结果，连打平也照写；只试过一次就写「That is one game, not yet a pattern」；还没测过的写「Not yet shown」。方法类、agent 类项目，再用一节讲清为什么有效：把机制拆开讲，规则冲突时听谁的。
- **有替代品就正面比。** 先承认替代品已经能做到什么，再说差别在哪。读者多半已经知道那个替代品，回避它反而显得心虚。关于替代品的说法也是事实，同样要有出处，比如官方文档或实测；查不到就别比。
- **安装只写读者还剩下的事。** 一条命令优先。紧跟着说清这条命令改了什么、装到了哪里，再列出只有人能做的步骤，比如授权、填 token、改默认值。仓库里真正要装的是哪个目录要明确说出来（「安装时不要把仓库根目录当作普通单个 skill 复制」）；依赖写明版本，并附一条确认命令和预期输出（`officecli --version  # 预期输出：1.0.151`）。可选依赖单独列出，写明什么情况下才需要。读者第一次试用很可能碰到「怎么没反应」，提前说一句并给出验证办法。
- **限制要说在前面。** 非官方、已停更、用了禁止商用或禁止修改的协议、免费版功能有缺：这些是读者最快的「不适合我」，越早说越节省他的时间。协议和项目宣传的用法互相矛盾时，提醒用户，但不替他改协议。
- **长短看有没有别的文档。** 有文档站或 `docs/` 的，README 只做门口，细节链出去，比如 process-compose 只有 107 行。没有的，README 本身就是文档，写到两三百行甚至更长都正常，高星的 skill 仓库多半是这样。长了就用问题当小标题（「它解决什么问题」「适合什么」「为什么有效」「重要边界」），超过 200 行左右加目录。不管多长，第一屏都要回答完「是什么、怎么用、会得到什么」。搬去别处不等于删掉，留下的链接要能点到。
- **作者喜欢的保留。** 徽章、logo、star 曲线这类装饰，作者没同意就不删。清单是为作者服务的，不是反过来。
- **高星仓库里也有不该学的。** 营销横幅、赞助链接和其他项目推荐挡在介绍前面、版本更新日志占据开头、`Made with Go`/`PRs Welcome` 这类没有信息量的徽章，都不要照搬。

文风：句子短，一句只说一个事实；能用数字的地方不用形容词。写完按 [references/ai-tone.md](references/ai-tone.md) 逐条扫一遍；中文 README 装了 `lieflat-less-ai-tone` 的，再用它过一遍句子。

中英双语的项目，中文版要意译而不是逐句直译：按中文技术写作的节奏重写，但小节、表格、链接、数字和英文版一一对应，方便机械核对。两份 README 的顶部互相链接。

### 5. 核验

README 是契约，交付前把它当契约查一遍：

1. **命令真跑。** 在 `/tmp` 下按 README 从零走一遍。跑不了的（要付费 token、要 OAuth 凭据），就从代码推断照着做会在哪一步失败、报什么错，并标明「读代码推断」。
2. 数字、默认值、路径逐个回代码核对。
3. 相对链接、图片、锚点都能打开。锚点用 `gh api /markdown` 渲染后核对，做法见 `gh-pr-traps` skill。
4. 图片和文字里没有私人信息，比如手机号、token、局域网 IP、住址。
5. **当一回陌生人。** 从头读一遍，记下自己会在哪一行想关掉页面。离开的位置如果不在你预期的地方，说明漏斗顺序错了。

### 汇报

改写时用一份决定清单汇报，不要贴全文。改了一份文档，最好审的是改动背后的决定：

```
改了什么（按读者能感到的变化写）
- 第一屏：…
搬走的：… → docs/xxx.md#yyy
删掉的：…（理由）
改正的不准说法：README:行，原来写…，代码里其实是…（文件:行）
没法核实 / 没实测：…
需要你定的：…
```

只审查时，用下面这个格式。每一节都要给出状态，没查的写「未核对」并说明原因，不能空着，也不能假装查过：

```
## README 审查：<仓库名>

读者和类型：<按第 1 步的表>　依据：<为什么这么判断>

### 第一屏：未核对 / 合格 / 有问题
### 事实（命令、数字、配置）：未核对 / 部分核对（核了 N 项，没核 M 项）/ 全部对上 / N 处不符
### 结构：未核对 / 合格 / 有问题
### AI 腔：未核对 / 没有 / N 处
### 隐私：未核对 / 干净 / 有问题

不合格的项（按对读者的伤害从大到小排）
1. [清单编号] 问题一句话。README:行（↔ 文件:行）。实测 / 读代码推断。

核对过、没问题的：…
没核对的、为什么：…
陌生人会在哪里离开：…
其他观察（对不上编号的）：…
```

每一项都要标出 [references/checklist.md](references/checklist.md) 里的编号（比如 `[F3]`）或 [references/ai-tone.md](references/ai-tone.md) 里的规则号（比如 `[AI-5]`）。对不上任何编号的，说明它不是这份 skill 定义的问题，单独列在最后的「其他观察」里，不混进不合格项。

## 最终验收

交付前逐条确认：

- 每一处改动都能对上某条规则（第 4 步的某一条、checklist 编号或 AI 腔规则号）。对不上的改动撤销，恢复原文。
- README 里每一条事实都能指出出处（信息守恒）。
- 原来的限制、限定说法都还在，语气没有被加重。
- 作者的内容没有被静默删掉；删了的都在汇报里写明。
- 「必须停下来问」的那几处，真的停下来问过了。
- 第 5 步的核验做完了，没做的在汇报里写明。

提交信息写读者能感到的变化，比如 `docs: say what this does in the first screen`，正文写为什么改、实测时发现了什么。推送之前先问用户。
