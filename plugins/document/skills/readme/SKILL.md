# readme

README 是读者对一个仓库的第一眼，很多人也只看这一眼。它要做的不是推销，而是让每个读者**尽快判断这东西适不适合自己**，包括尽快发现不适合、然后离开。所以 README 要写成一个漏斗：最影响去留的事实放最上面，越往下越细，细到只有决定留下的人才需要的程度，就该离开 README、进 `docs/` 了。

README 同时是一份契约：它说这个项目做什么、怎么用，读者照着做就该得到那个结果。所以 README 里的每条命令、每个数字都必须是真的。一句编出来的参数比少写一句更伤人，因为读者会照做，然后失败。

这两条是下面所有规则的来源。碰到规则没覆盖的情况，回到这两条去判断。

## 什么时候不用

- 用户要写完整的文档站、教程、API 参考：那是 `docs/` 的活，README 只给它们指路。
- README 已经好用，用户只是想换个风格：没有读者受益的改动不做。
- 只想改一个错字、补一行：直接改，不用走下面的流程。

## 流程

### 1. 先弄清是谁在读

不同读者要的东西完全不同，弄错读者，后面每一步都会偏。

| 仓库类型 | 读者，以及他们最想知道什么 | 漏斗顺序 |
|---|---|---|
| 工具 / App / CLI | 路过的陌生人：这是什么、长什么样、装得上吗 | 一句话 → 真实画面 → 怎么装 → 限制 → 细节链接 |
| 库 / SDK | 要调用它的开发者：接口顺不顺手 | 一句话 → 最小可运行示例及其输出 → API 概览或链接 → 安装 → 限制 |
| 有在线 Demo 的 Web App | 想先试的人；只有少数人会自己部署 | 一句话 → 截图和 Demo 链接 → 自托管（必填配置、外部服务、部署限制） |
| 私人工具 / 运维仓库 | 将来的自己、接手的 agent：要做 X 该读哪份、碰哪里会坏 | 一句话（是什么、跑在哪）→ 按任务指路 → 目录 → 不显然的决定 → 怎么装 → 出问题怎么办 |
| 课程作业 / 研究 | 老师、面试官：做了什么、结果如何 | 一句话 → 结果（数字或图）→ 怎么复现 |

库把安装放在 API 后面，是因为读者要先看接口合不合用，才愿意去装。App 没有接口给人看，所以装法紧跟在画面后面。

看不出读者是谁就问用户一句。别按开源项目的默认模板去写一个配置文件夹。

### 2. 收事实

动笔前先读代码，把 README 要写的事实逐条列出来，每条都带上出处（`文件:行`）：

- 安装脚本**实际**做了什么：装到哪、改了用户的哪些设置、不碰什么
- 配置项：变量名、默认值，哪些是必填。代码、`.env.example`、compose 文件三处要对上
- 行为里的具体数字：阈值、间隔、上限
- 依赖和最低版本：以 CI 真跑过的版本为准
- 外部服务：OAuth、第三方 API、构建时要联网抓的东西，以及它们挂掉时项目会怎样
- 限制：免费版缺什么、哪些平台不支持
- 卸载：安装时改过的每一处，都要有对应的撤销步骤

核实不了的说法不写进 README，交付时单独告诉用户。

### 3. 先审，再改

已有 README 的话，先从头读一遍，对照漏斗找下面这些毛病。它们是真实审查里最常见的：

- **读者混在一起。** 发版流程、CI 密钥表、目录树、调试指南，和给用户看的内容搅在一起。这是最常见、伤害最大的一种。`CLAUDE.md`、`AGENTS.md` 也算这一类：它们是写给 agent 的指令，不能当成「架构文档」从 README 推荐给读者。例外是专门写给 agent 照着做的文档，比如 `docs/agent-install.md`，可以从安装一节链过去。
- **漏斗塌了。** 前 50 行就在讲内部实现，读者还不知道这东西是不是给自己的。
- **同一件事说了几遍。** 版本号、阈值在三个地方各说一次，迟早有一处会过时。
- **过时。** 链接失效、提到已删除的文件，命令早就改了。
- **说法比代码大。** 写着有的功能其实没有，写着「可选」的其实是必填，没实现的写成已有。
- **读起来像生成的。** 满屏加粗、每节一张表、emoji 小标题、三连排比、面面俱到的 FAQ、「强大 / 无缝 / 一站式」这类词。读者一眼认出来，就不再相信后面的内容。

动手前还有三件事：
1. 跑 `git status`。工作区不干净就别直接改，README 可能带着作者还没提交的东西。
2. grep 一下测试和 CI 里有没有钉死 README 文字的断言（标题、文件列表），否则改完 CI 会红。
3. 看看有没有派生副本（`README.zh-CN.md`、官网文案、包管理器上的描述），它们要一起改，或者明确说这次不改。

用户只要审查的话，到这里就停：按下面「汇报」一节的格式出报告，不动文件。

### 4. 写

按第 1 步的漏斗顺序写。下面每一层都是作者在自己最好的几个仓库里反复改出来的做法，具体例子见 [references/examples.md](references/examples.md)。

- **一句话说效果，不说技术。** 读者要知道的是「它替我做了什么」，不是「它用什么写的」。能带一个对照最好：「不告诉你今天有雨，告诉你几点下、几点停。」GitHub 仓库的 About 描述要和这句说的是同一件事。
- **紧接着放真实的东西。** 实机截图、真实输出、录屏都行。读者信眼睛不信形容词，mockup 和 AI 生成的图会让人起疑。先去仓库里找（`docs/`、`screenshots/`、release 附件），常常已经截好了只是没用上；截图必须和现在的界面一致，导航、文案已经改过的旧截图会让读者以为东西没维护。真没有合适的就留空，请用户截，不要自己造。
- **一段场景比一串功能好记。** 用两三句写读者原本的处境，以及这东西出现之后有什么不同。
- **功能写成结论加数字。** 「3 分钟以内不提醒，10 分钟以上才响铃」比「智能提醒」有用，因为读者能拿它和自己的情况对比。
- **有替代品就正面比。** 先承认替代品已经能做到什么，再说差别在哪。读者多半已经知道那个替代品，回避它反而显得心虚。关于替代品的说法也是事实，同样要有出处，比如官方文档或实测；查不到就别比。
- **安装只写读者还剩下的事。** 一条命令优先。紧跟着说清这条命令改了什么、装到了哪里，再列出只有人能做的步骤，比如授权、填 token、改默认值。读者第一次试用很可能碰到「怎么没反应」，提前说一句并给出验证办法。
- **限制要说在前面。** 非官方、已停更、用了禁止商用或禁止修改的协议、免费版功能有缺：这些是读者最快的「不适合我」，越早说越节省他的时间。协议和项目宣传的用法互相矛盾时，提醒用户，但不替他改协议。
- **细节链出去。** 完整配置、原理、排障、设计取舍放进 `docs/`，README 里留一行链接就够了。正文（不算代码块）超过 150 行左右，通常就说明有东西该搬走了。搬走不等于删掉，留下的链接要能点到。
- **作者喜欢的保留。** 徽章、logo、star 曲线这类装饰，作者没同意就不删。清单是为作者服务的，不是反过来。

文风：句子短，一句只说一个事实；能用数字的地方不用形容词。粗体只留给读者会踩的坑。表格只在有两个以上维度需要对比时才用。写完对照 [references/checklist.md](references/checklist.md) 里的「AI 腔」一节扫一遍。

中英双语的项目，中文版要意译而不是逐句直译：按中文技术写作的节奏重写，但小节、表格、链接、数字和英文版一一对应，方便机械核对。两份 README 的顶部互相链接。

### 5. 核验

README 是契约，交付前把它当契约查一遍：

1. **命令真跑。** 在 `/tmp` 下按 README 从零走一遍。跑不了的（要付费 token、要 OAuth 凭据），就从代码推断照着做会在哪一步失败、报什么错，并标明「读代码推断」。
2. 数字、默认值、路径逐个回代码核对。
3. 相对链接、图片、锚点都能打开。锚点用 `gh api /markdown` 渲染后核对，做法见 `gh-pr-traps` skill。
4. 图片和文字里没有私人信息，比如手机号、token、局域网 IP、住址。
5. **当一回陌生人。** 从头读一遍，记下自己会在哪一行想关掉页面。离开的位置如果不在你预期的地方，说明漏斗顺序错了。

### 汇报

改写时用一份决定清单汇报，不要贴全文。改了一份文档，最好审的是改动背后的决定：

```
改了什么（按读者能感到的变化写）
- 第一屏：…
搬走的：… → docs/xxx.md#yyy
删掉的：…（理由）
改正的不准说法：README:行，原来写…，代码里其实是…（文件:行）
没法核实 / 没实测：…
需要你定的：…
```

只审查时，只列不合格的项，每项给出位置。问题出在 README 以外的，写成「README:行 ↔ 文件:行」。最后加一段「陌生人会在哪里离开」。

提交信息写读者能感到的变化，比如 `docs: say what this does in the first screen`，正文写为什么改、实测时发现了什么。推送之前先问用户。
